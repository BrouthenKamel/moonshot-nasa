# Moonshot v1.0: Lunar Ice Mapper, single-mission loop end to end

## Context

NASA Space Apps 2026, challenge "Space Mission Design Game". The repo is an empty scaffold (Vite + React 19 + TypeScript + Tailwind 4 + react-three-fiber + Zustand + Zod + Vitest; `src/sim`, `src/data`, `src/state`, `src/scene`, `src/ui` hold only `.gitkeep`; `src/App.tsx` is a title placeholder). Nothing to reuse beyond the stack and folder layout described in `README.md`.

The team's board (`docs/human/brainstorming_board.md`) decided: one fixed brief (Lunar Ice Mapper, 6U CubeSat to lunar polar orbit), a 9-step core loop owned by four roles (Ground, Science, Space, Launch), one player plays every role for now, turn = one month. Campaign layer (agency, publicity, Mars) is explicitly "later" and is out of v1.0.

v1.0 = that 9-step loop, playable from brief to report and replayable, scoring well against `docs/hackathon/checklist.md`.

## Decisions I am making where the board says "still to set"

These are defaults so the build is not blocked; all live in one data file and are easy to change.

| Open item on the board | v1.0 default |
|---|---|
| Data target X | 10 GB returned to the ground (Engineer difficulty) |
| Budget cap Y | $16M (Engineer); 20 / 16 / 13 across the three difficulties |
| Missed ride | Wait for the next ride 6 turns later and pay team cost each waiting turn (not an instant fail) |
| Phases by segment or by people | By segment (the four NASA segments), each step tagged with its role colour |
| Data units, storage | GB per turn; onboard storage fills, overflow is lost |
| Relays | Not in v1.0 |
| Fail vs partial | As on the board: no capture or contact lost = fail; data or coverage short = partial |
| Score weights | 1000 pts: requirements 600, science 200, efficiency 100, risk handling 100 |

Three additions beyond the board, each because the checklist asks for it and it is cheap:

1. **Ride choice in step 5** (checklist: launch vehicles with different capacity, cost, orbit, plus a compatibility check). Three rideshares: the board's default lunar ride on turn 8 (dropped on a trans-lunar path), a cheaper GTO rideshare on turn 6 (much more delta-v needed, realistically electric only), a pricier commercial lunar ride on turn 10 (dropped near the Moon, small capture burn). Each has a mass limit and a drop-off orbit; Go/No-Go checks mass and delta-v against it.
2. **Three difficulty levels** (Cadet, Engineer, Flight Director): budget cap, event odds, data target, and how much the UI explains up front.
3. **Team mode as pass-and-play** on one machine: up to four named players each take a role; each step shows whose turn it is, and Go/No-Go needs a sign-off from every role, with each role shown the bar it cares about. Networked multiplayer is out of scope.

## Architecture

Pure logic in `src/sim` (no React, unit-tested), numbers in `src/data`, one Zustand store, UI reads derived values only. This matches the README layout.

### `src/data/` (balance tables, Zod-validated at load)
- `brief.ts`: mission brief, requirements, difficulty presets, turn constants.
- `parts.ts`: catalogue per category (structure, solar panels, batteries, radio/antenna, computer, attitude control, propulsion, instruments). Every part: mass kg, volume U, power W (draw or generation), cost $M, build months, plus category-specific fields (data GB/turn, science value, Isp, propellant kg, storage GB, reliability).
- `orbits.ts`: polar science orbits (about 50 / 100 / 200 km and a frozen elliptical option): coverage rate, resolution factor, station-keeping delta-v per turn, eclipse fraction.
- `rides.ts`, `transfers.ts`: rides as above; transfers fast (about 1 turn, high delta-v) vs low-energy (several turns, low delta-v), with compatibility by propulsion type.
- `ground.ts`: own small dish, university partner dish, rented deep-space network time: cost per turn, contact hours, rate multiplier.
- `events.ts`: clogged thruster (Lunar Flashlight), lost contact after deployment (Lunar IceCube), radiation reset, budget cut, solar storm, reaction wheel fault; each with base odds, mitigations, and choices.
- `reference.ts`: Lunar IceCube, Lunar Flashlight, LRO facts for the comparison table.
- `glossary.ts`: plain-language explanations (delta-v, eclipse, link rate, margin, 6U) used by tooltips.
- `sources.ts`: per-table citation to the NASA resource it comes from.

**Validity note:** I cannot run GMAT here and CubeSat 101 is not in `docs/resources`. Numbers will come from published figures for these missions and tools as I know them, each tagged in `sources.ts` as `sourced` or `gameplay-tuned`. Delta-v is computed with the real rocket equation from the player's mass, propellant and Isp, so the trade is physically honest even where inputs are rounded. The team should spot-check the tables before the pitch.

### `src/sim/`
- `types.ts`: `Design` (all step 1 to 6 choices), `Budgets`, `SimState`, `TurnAction`, `TurnLog`, `Report`.
- `budgets.ts`: `computeBudgets(design)` → mass, volume, power in sun and in eclipse, cost (parts + ride + ops + testing), reserve, delta-v available vs required (transfer + capture + station-keeping × 12), data made vs downlink capacity per turn, build schedule vs ride turn, failure-odds modifiers. This is what makes every choice visibly move other meters.
- `checks.ts`: `goNoGo(design)` → six resource bars (mass, power, budget, data, comms, time) with green/yellow/red, a plain-words reason, and the step to fix. Hard blockers per the board's rule plus ride compatibility.
- `rng.ts`: seeded PRNG so a run is reproducible and testable.
- `simulate.ts`: `initSim(design, seed)` and `stepTurn(state, action)`: build and test turns, ride, transfer, capture burn, then orbit turns (energy balance with battery through eclipse, coverage growth, data made / stored / sent / lost, fuel use, events). Per-turn player actions: operating mode (full science, one instrument off, safe mode), buy an extra downlink pass, spend reserve on an event fix. Every loss is logged with a cause code pointing at the decision that produced it.
- `evaluate.ts`: `buildReport(state)`: each requirement met or missed with the traced reason, outcome level, score breakdown, "what to change next time" hints, comparison rows.
- Tests beside each file, including balance tests: at least three clearly different designs reach full success on Engineer; the "buy the best of everything" design fails Go/No-Go; a fixed-seed full play-through is deterministic.

### `src/state/gameStore.ts`
Zustand with `persist`: screen/step, mode (solo or team, player names), difficulty, current design, sim state, run history (design + report) for retry, compare and a local ranking. Design export/import as a short code for sharing.

### `src/ui/`
- Shell: header (mission, turn, difficulty), step rail with role colours, and an always-visible **resource dashboard** (the six bars with margins) that updates live on every choice.
- `steps/`: Brief, 1 Planning, 2 Instruments, 3 Spacecraft, 4 Orbit, 5 Ride and transfer, 6 Comms, 7 Go/No-Go. Option cards show cost in every resource and a "why this matters" line; steps stay revisitable until Go.
- `SimScreen`: turn timeline, event cards with choices, live telemetry, turn log.
- `ReportScreen`: requirement checklist with reasons, score, comparison with real missions, run history, "try again with changes" (keeps the design).
- `Explain` tooltip and a first-run guided intro on Cadet.

### `src/scene/` (react-three-fiber, procedural, no external assets)
- `SpacecraftView`: the 6U box filling with coloured part blocks, deployable panels, overflow shown in red (step 3).
- `MissionView`: Earth, Moon, transfer path, polar orbit ring at the chosen altitude, south-pole coverage growing during the sim.
Lazy-loaded so the game still works if WebGL fails.

## Build order

1. Data tables + types + `budgets` + `checks`, with tests.
2. `simulate` + `evaluate` + balance tests (game fully playable headless).
3. Store, shell, dashboard, the eight design screens.
4. Sim and report screens, run history and compare.
5. Difficulty, team pass-and-play, tooltips and intro.
6. 3D views.
7. Self-review against `docs/hackathon/checklist.md`; update `README.md` (how to play, NASA resources used).

Stopping after step 4 already gives a complete game; 5 and 6 are layered on without touching the sim.

## Out of scope for v1.0

Campaign and publicity layer, further mission briefs (the brief is data-driven so they can be added), networked multiplayer, online leaderboard, sandbox mode, NASA imagery mini-tasks.

## Verification

- `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm build` all clean.
- Headless play-through tests with fixed seeds covering full success, partial, and each fail path.
- Run `pnpm dev` and play through in the browser: one winning design, one No-Go bounce back to step 3, one failure, then retry and compare; check team mode sign-off and that the 3D views render.
- Final pass: a line-by-line table of the checklist with covered / partial / not covered, reported back to you.
